# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## ⛔ Security: never publish a fix for deployed code

The programs here are **deployed on-chain and hold user funds.** You usually **cannot tell** whether a given program is already deployed — so do not try to guess. Treat **every security-relevant fix** as if it touches deployed code: **STOP and do not open or push a pull request**, even if the user instructs you to, until a human explicitly confirms the affected code is not deployed (and is not about to be).

Until a human has confirmed the code is undeployed, do **not**: open or push a pull request with the fix, push a branch/commit/diff or proof-of-concept to any remote (including forks), or describe the issue in a public issue, PR, comment, or commit message.

Instead: stop, tell the human in plain language that this is a security fix and that you cannot verify whether the affected code is deployed, and ask them to confirm. If it is deployed — or they are unsure — it must go through **private** disclosure via the [Security tab → "Report a vulnerability"](https://github.com/eco/eco-routes-svm/security), not the normal PR flow. The exposure happens at the **push** to a public remote, not the merge, and a later revert does not undo it — a fix for deployed code is developed only in the private advisory fork, never pushed here. Full policy: [`SECURITY.md`](./SECURITY.md). This is a hard safety constraint.

## Repository

Anchor (1.1.2) workspace implementing a cross-chain intent protocol on Solana. Rust 1.97.1 (`rust-toolchain.toml`); release profile uses `lto = "fat"`.

Two toolchains matter and they are not the same one. `rust-toolchain.toml` is the **host**
compiler (clippy, tests, `avm`). The **on-chain** programs are compiled by the rustc inside
Solana's platform-tools — currently 1.89.0-dev, older than the host. Anything in program code
or in a dependency of `eco-svm-std` must compile under *that* rustc, so a new-ish stdlib method
or a dependency raising its MSRV will break the on-chain build while the host build stays green.

**`anchor build` picks that compiler, not the installed Solana CLI.** anchor-cli 1.x hard-codes
`--tools-version v1.52` when it shells out to `cargo build-sbf`, so `SOLANA_VERSION` pins the CLI
tooling but does *not* decide the bytecode compiler — bumping `ANCHOR_VERSION` can change it
instead. (0.31.1 passed no `--tools-version` and got v1.43 / 1.79.0-dev from the CLI default, so
the 0.31.1 → 1.1.2 upgrade moved the on-chain compiler from 1.79.0-dev to 1.89.0-dev.) CI asserts
the SBF rustc after every build (`scripts/assert-sbf-rustc.sh`) so this cannot change silently.

## Build / test / lint

```bash
# Build all programs (writes .so to target/deploy/)
anchor build                 # localnet — includes dummy-ism
anchor run build-devnet      # excludes dummy-ism
anchor run build-mainnet     # adds --features mainnet to every program (REQUIRED for mainnet)

# Tests use litesvm and embed the .so files via include_bytes!, so anchor build
# (or build-localnet) must run before `cargo test` or the binaries are stale.
anchor test                  # build + cargo test
cargo test --no-fail-fast
cargo test --test flash_fulfill                 # one integration test file
cargo test --package portal mark_fulfilled      # one unit test
cargo test -- --nocapture

# Goldie snapshot updates (assert_json! / assert_debug! / assert_yaml!)
GOLDIE_UPDATE=1 cargo test

# Lint — DO NOT pass --all-features. portal's `cpi` feature breaks Anchor codegen
# (it implies `no-entrypoint`, which strips the program module that other crates' CPI helpers reference).
cargo clippy --all-targets -- -D warnings
cargo +nightly fmt           # nightly required (group_imports = StdExternalCrate)
cargo sort --workspace       # CI runs --check
```

`mock-igp` and `mock-prover` (in `integration-tests/programs/`) are **not** Anchor programs and `anchor build` skips them. `mock-prover` reads proofs under runtime program IDs to exercise eight-member aggregation. CI builds it explicitly:

```bash
cargo build-sbf --manifest-path integration-tests/programs/mock-igp/Cargo.toml --sbf-out-dir target/deploy
cargo build-sbf --manifest-path integration-tests/programs/mock-prover/Cargo.toml --sbf-out-dir target/deploy
```

If proof-helper / pay_for_gas integration tests fail with a missing `.so`, run that command.

The confused-deputy PoC programs `malicious-prover` and `malicious-proof-closer`, and the localnet mocks `mock-polymer-prover` and `mock-layerzero-endpoint`, **are** Anchor programs (in `programs/`, like `dummy-ism`), so a bare `anchor build` builds them. What keeps them out of devnet/mainnet artifacts is **not** the `[programs.localnet]` registration — `[programs.<cluster>]` only maps names to IDs. It is the explicit `--program-name` enumeration in the `build-devnet` / `build-mainnet` scripts (`Anchor.toml`) and the `RELEASED_PROGRAMS` list `release.yml` copies assets by. **Never replace those enumerations with a bare `anchor build`** — doing so would ship the PoC programs.

## Architecture

Eight production on-chain programs (plus the localnet-only `dummy-ism`, `mock-polymer-prover`, `mock-layerzero-endpoint`, `malicious-prover`, and `malicious-proof-closer` test programs) and one shared crate. `eco-svm-std` (`packages/eco-svm-std`) defines `Bytes32`, `Proof`/`ProofData`/`ProveArgs`, and the generic `prover::cpi::prove` CPI helper used by local-prover callers. Other prover account layouts are assembled by Portal's variable-account dispatch.

```
        publish/fund                 fulfill              prove (CPI dispatch)         handle (Hyperlane inbound)
User ───────────────► Portal ◄──── Solver ───► Portal ──────────► HyperProver ─────────► HyperProver ──► Portal.withdraw
                       │                                              │  ▲                    │
                       │ withdraw (CPI validation)                   │  │ same-chain         │
                       └──────────────► LocalProver / HyperProver     │  │                    │
                                                                      │  │  flash_fulfill     │
                              FlashFulfiller ──prove→ LocalProver ────┘  │  (atomic)          │
                                       │   ──withdraw/fulfill→ Portal ───┘                    │
                                       └─ sweep leftovers → claimant                          │
```

Polymer is pull-based — the bridge never calls us:

```
  Relayer ──create_accounts / load_proof──► Polymer program          (stage the proof)
     └─────► PolymerProver.validate ──CPI validate_event──► Polymer program
                    └─► Proof PDA ────────────────────────► Portal.withdraw   (later, by anyone)

  Portal ──prove (CPI dispatch)──► PolymerProver ──`Prove: program: <id>, <hex>` log──► EVM PolymerProver.validateSolana
```

### Programs (`programs/*`)

- **aggregator-prover** — immutable 1–8 member config. `get_proof` takes any subset of members, each at most once, and returns the first `Some(Proof)` in caller order; `None` requires every member (`IncompleteProverSet` otherwise). Opaque query data encodes `Vec<MemberQuery { account_count, data }>`; each member receives its own variable-length account slice and data. Framing and membership (configured, unique) are checked before any query. `close_proof` closes every supplied member group with Portal’s intent-scoped signer. Cancellation cleanup queries and closes the same tail; the first returned proof must be a cancellation. No `aggregate`, own proof PDA, `IntentProven` event or `prove` instruction. CPI depth/reentrancy restrictions still apply. Account framing and client changes: `docs/prover-interface.md`.
- **portal** — `publish`, `fund`, `fulfill`, `cancel`, `prove`, `withdraw`, `refund`, `close_proof`. Owns permanent destination `FulfillMarker` and source `WithdrawnMarker` accounts. `withdraw` and `refund` query `reward.prover` through `eco_svm_std::prover::cpi` and leave proofs intact. `GetProofArgs` carries `intent_hash`, `destination` and opaque `data`. Provers answer `None` for another destination's proof, so the aggregator moves past it to the next member; `cpi::get_proof` rejects a returned proof for another destination as malformed. Destination filtering must stay in the provers: Portal sees only the aggregator's first proof, so it can neither skip a mismatch nor treat it as absence. Refund is stateless, chooses its path from the withdrawal marker and `Option<Proof>`, and sweeps whatever token triples it is given. `close_proof` is independent and requires either an authentic withdrawal marker or a validated cancellation at/after that deadline. It signs `proof_closer_pda(intent_hash)` with seeds `[b"proof_closer", intent_hash]`. Every concrete closer must bind BOTH that signer and its proof PDA to the same hash. The hash already commits to `reward.prover`; no separate prover seed is needed. Refund never records a cancellation marker. `cancel` writes the shared cancellation claimant to the permanent destination marker; `fulfill` rejects it. Portal uses semantic std helpers, never the raw cancellation sentinel.
- **local-prover** — same-chain prover. `prove` is gated to two callers only: portal's `dispatcher_pda(&local_prover::ID)` (for cross-chain bridging) and flash-fulfiller's `prove_authority_pda(&local_prover::ID)` (for atomic flash fulfillment). Flash-Fulfiller uses the shared `prover::cpi::prove` CPI helper; Portal assembles its variable account list. **Both authorities are prover-scoped and this is a load-bearing security boundary** — the caller signs a PDA seeded by the program it is dispatching *to*, and each prover accepts only the PDA scoped to its *own* ID. `portal::prove` and `flash_fulfill` both sign these PDAs into a caller-chosen, ID-unvalidated prover program (portal has no dep edge to any prover; flash-fulfiller's `local_prover_program` can't be pinned without a dependency cycle), so the scoping is what keeps the signer meaningful. Keep it: do not collapse either authority to a single shared PDA. `flash_vault` is deliberately **not** a prover credential — it is the fund-holding/solver/withdraw-claimant identity signed into caller-chosen programs, so it must never be added as a prover caller.
- **hyper-prover** — Hyperlane-backed prover. `prove` dispatches via `MAILBOX_ID` (mainnet vs non-mainnet pubkey gated on the `mainnet` feature). `handle` is the Hyperlane recipient entrypoint; uses **custom instruction discriminators** (`HANDLE_DISCRIMINATOR`, `HANDLE_ACCOUNT_METAS_DISCRIMINATOR`, etc.) defined in `hyperlane.rs` rather than Anchor-derived ones — Hyperlane requires fixed function selectors. The `ism` instruction returns `None`, so message verification uses the mailbox's default ISM (no custom ISM is configured).
- **flash-fulfiller** — atomic same-chain orchestrator: `local_prover.prove → portal.withdraw → portal.fulfill → sweep`. Lives in its own program (rather than as a `local-prover` instruction) to dodge Solana's reentrancy rule — `local_prover` only appears once on the stack, inside portal's `get_proof` CPI. Also offers a buffered-intent flow: `set_flash_fulfill_intent` / `append_flash_fulfill_intent_chunk` write a `(route, reward)` payload to a per-(writer, intent_hash) PDA so callers can later invoke `flash_fulfill` by hash alone.
- **polymer-prover** — Polymer-backed prover, pull-based unlike hyper-prover: nobody calls us, a relayer loads a Polymer proof into Polymer's program (`create_accounts` → `load_proof`) and then calls our permissionless `validate`, which CPIs Polymer's `validate_event` and reads the `["result", authority]` account it writes **in the same instruction** (freshness), then mirrors the Solidity `PolymerProver.validate` checks (whitelisted emitter, `IntentFulfilledFromSource` selector, topic 1 == `CHAIN_ID`, payload destination == Polymer's `chain_id`) and creates `Proof` PDAs idempotently (same proof no-op, disagreeing proof `IntentAlreadyProven`). `prove` is gated to `dispatcher_pda(&polymer_prover::ID)` and emits one `Prove: program: <id>, <hex>` log per intent (hex = source u64 ‖ destination u64 ‖ intent hash ‖ claimant) for the EVM `PolymerProver.validateSolana` to parse — that string is a shared ABI. Polymer's Prove API hands back only the `<hex>` payload (it strips the whole `Prove: program: <id>, ` head, seen on devnet), so the EVM side binds the program through `validateSolLogs`' authenticated `programID`; it accepts both forms. `polymer.rs` hand-mirrors Polymer's IDs (mainnet `CdvSq48Q…`, devnet `FtdxWoZX…`, feature-gated), PDAs, discriminators and result layout the way `hyperlane.rs` mirrors the mailbox; Polymer's public docs describe an older interface, their repo source (v1.0.4) is authoritative. Callers set a 1.4M CU limit on `validate`. Operational notes: (1) `validate` has no partial-batch mode — every pair in the event needs its Proof PDA in one transaction — so keep EVM `Inbox.prove` batches destined for Solana at or below `MAX_INTENTS_PER_PROVE` (24), the same cap as the outbound direction, and deliver it with a v0 transaction plus an address lookup table — a legacy transaction tops out at 23 pairs (`MAX_PAIRS_PER_VALIDATE_LEGACY_TX`). The real ceiling is the 64-entry instruction trace: 30 fresh pairs, and an adversary who pre-funds 7 Proof PDAs pushes a 24-pair batch over it; account locks (54), CU (~252k of 1.4M) and Polymer's `unindexed_data` cap (~45) never bind. `MaxInstructionTraceLengthExceeded` means re-prove with a smaller batch — the intent is not lost, only the Polymer proof. Full derivation lives in `validate.rs::mark_intent_hashes_proven`'s doc comment; keep validate.rs, CLAUDE.md and spec 3.4 in sync. (2) The 10 KB log buffer `MAX_INTENTS_PER_PROVE` defends is per *transaction* while the cap is per instruction, so submit `portal::prove` as the only log-emitting instruction in its transaction (a full 24-intent batch overruns the 1232-byte packet — 24 FulfillMarker accounts plus 24 hashes — so send it as a v0 transaction with the markers in an address lookup table, as for `validate`), then count the `Program log: Prove: program: <polymer_prover id>, ` lines in `meta.logMessages` against the hashes sent and resubmit any shortfall — `prove` writes no state, so the retry is safe.
- **layerzero-prover** — LayerZero V2-backed prover, both directions; liveness member for the 1-of-N aggregator. **Outbound is two-step**: `prove` (gated to `dispatcher_pda(&layerzero_prover::ID)`) only commits the batch to a content-addressed `PendingSend` PDA, and a permissionless top-level `send_message` CPIs `endpoint::send` — `send` nests endpoint → ULN → worker → pricefeed, which already fills Solana's 5-frame invoke stack, so it cannot run under `portal::prove` (SIMD-0268, raising the limit, was not active when this shipped). Solver: `[ComputeBudget, portal::prove, layerzero_prover::send_message]` in one v0 transaction with ALTs, fee from simulating `quote_message`; batch ≤ `MAX_INTENTS_PER_PROVE` (21, measured with that transaction shape: 62 of 64 account locks). The margin is thin: the cap assumes one ALT and ≤ 4 DVNs per path; a second ALT pushes 21 over the 1232-byte packet, and the fallback is `portal::prove` and `send_message` in separate transactions (the `PendingSend` commit persists). Options are computed on-chain with the EVM gas floor (`200_000 + 50_000·n`). **Inbound** is LayerZero's executor V2 flow: `lz_receive_types_info` (returns `[store, store.alt]`, the accounts v2 takes) → `lz_receive_types_v2` (returns `lz_receive_accounts` compacted against that lookup table as LayerZero's `compact_accounts_with_alts` does: every table member becomes `AltIndex(0, i)`, only the per-message PayloadHash and Proof PDAs stay `Address`; `lz_receive_accounts` stays plain and must remain the single source of the account list `lz_receive` validates) → `lz_receive`, which CPIs `endpoint::clear` first, then checks `sender == peer[src_eid].address` and `ProofData.destination == peer.chain_id`, then creates `Proof` PDAs like `hyper-prover::handle` (identical redelivery no-op, conflict `IntentAlreadyProven`). Proof rent comes from the `pda_payer` reserve because the EVM sender's options carry gas only; an empty reserve makes delivery fail retryably, so monitor its balance. **Prover interface** (`docs/prover-interface.md`), as hyper-prover: `get_proof` answers through the shared `Proof::get` (query tail `[proof]`, data ignored); `close_proof` binds Portal's intent-scoped `proof_closer_pda(intent_hash)` and `Proof::pda(intent_hash)` and refunds the rent to `pda_payer` (cleanup tail `[proof, pda_payer]`, non-signer). `withdraw` leaves the proof, and only `pda_payer` profits from Portal's permissionless `close_proof`, so the reserve is only refilled if the operator bundles cleanup with `withdraw` or runs it from a job. EVM `Inbox.prove` batches toward Solana must stay ≤ `MAX_PAIRS_PER_MESSAGE` (6, measured on devnet: LayerZero's executor refuses delivery transactions over 1220 bytes; 6 pairs delivered at 1142, 7 measured 1227) — the EVM `LayerZeroProver` must pin the Solana pathway's `maxMessageSize` to 392 bytes so larger batches revert at send; an over-cap verified message can still be executed by hand with a lean `[compute-limit, lz_receive]` v0 transaction and our lookup table (7 pairs: 1079 bytes). The EVM `LayerZeroProver` must whitelist the **`Store` PDA** (the OApp address LayerZero reports as `origin.sender`), not the program ID, and map Solana's EID (30168 mainnet / 40168 devnet) to `CHAIN_ID`. **Admin model**: `pda_payer` is the LayerZero delegate; `init` / `add_peers` / `init_path` / `set_path_config` / `set_alt` are gated on the program's upgrade authority, so finalizing the program is the delegate revocation; the peer set (≤ `MAX_PEERS` = 32; `init` fits ~18 per transaction, `add_peers` appends the rest and clears the recorded ALT) is fixed at finalization. Every path must be fully pinned (ULN302 send/receive library, explicit DVNs, confirmations, executor — `set_path_config` rejects LayerZero defaults and `NIL_CONFIRMATIONS`, which ULN302 resolves to 0 confirmations) and read back before finalizing; an unpinned path after finalization needs a new program ID. **Finalization gate:** before finalizing, run one real outbound `send_message` and one inbound executor delivery on every configured mainnet path and read back each path's Nonce, send/receive library and ULN send/receive + executor config — ULN302 `init_config`/`set_config` tails, `SendParams`/`QuoteParams` and the `send` account head are only verified against the mock in CI (a 2026-10-08 devnet E2E against Base Sepolia passed both directions on the real programs, but each mainnet path still needs its own run). Operational traps: (1) `set_path_config` runs ULN302 `init_config`, which creates the per-OApp Send/ReceiveConfig accounts, so on a real chain it is one-shot per eid — a wrong config must be corrected by a program upgrade before finalizing, then read back again; (2) the inbound lookup table must contain every account `required_alt_addresses` lists (the static `lz_receive` accounts — Store, `pda_payer`, system program, our event authority and ID, endpoint ID, OApp registry, endpoint settings and event authority — plus every peer's Nonce) and be frozen and active; `set_alt` enforces all of that on-chain (`InvalidLookupTable`, `LookupTableNotFrozen`, `LookupTableDeactivated` or `LookupTableMissingAddress` otherwise; `AltNotSet` is `lz_receive_types_v2` before any table is recorded), because after finalization it can never replace the table; (3) `pda_payer` must be pre-funded before `init_path` / `set_path_config` (it pays endpoint/ULN rent as delegate) and kept funded for inbound proof rent. `layerzero.rs` hand-mirrors LayerZero-v2@9c741e7f (endpoint/ULN IDs, big-endian seeds, discriminators, V2 executor types); the `#[ignore]`d `integration-tests/tests/layerzero_prover_real.rs` (needs `LZ_ENDPOINT_SO`) checks it against the dumped endpoint binary.
- **mock-polymer-prover** — localnet-only stand-in at Polymer's devnet ID with identical account layouts; its `validate_event` decodes the loaded cache as a `ValidationResultAccount` so tests inject any EVM event.
- **mock-layerzero-endpoint** — localnet-only stand-in for the LayerZero endpoint; never part of devnet/mainnet builds, deploys, or release IDLs.
- **proof-helper** — off-chain/test helper for Hyperlane gas payment (`pay_for_gas`).
- **dummy-ism** — local-only fake ISM, included in `[programs.localnet]` only; excluded from devnet/mainnet builds.

### Cross-cutting conventions

- **Intent hash** is the address-key for almost every PDA: `vault_pda`, `WithdrawnMarker::pda`, `FulfillMarker::pda`, `Proof::pda` (per-prover). Computed as `keccak(destination || route_hash || reward_hash)` in `portal::types::intent_hash`. Source and destination chains MUST agree on the hash byte-for-byte — `Bytes32`, `Route`, and `Reward` use Anchor/Borsh serialization with field order that is part of the on-chain ABI.
- **`CHAIN_ID`** is feature-gated in `eco-svm-std/lib.rs` (mainnet vs non-mainnet) and is used in proof and intent-hash computation. Forgetting `--features mainnet` produces silently-mismatched intent hashes against mainnet counterparts.
- **`mainnet` feature** propagates: `eco-svm-std/mainnet` flips `CHAIN_ID`; `hyper-prover/mainnet` flips `MAILBOX_ID`; every production program enables it via `eco-svm-std/mainnet`. `flash-fulfiller`'s `mainnet` also implies `custom-heap`.
- **Token transfers (`programs/portal/src/types.rs`)** — `VecTokenTransferAccounts` parses `remaining_accounts` in chunks of 3: `[from, to, mint]`. Used by `fulfill`, `withdraw`, and `flash_fulfill`. Both `spl-token` and `token-2022` are supported; mint owner is the discriminator.
- **`prover::cpi::prove` CPI** (`packages/eco-svm-std/src/prover/cpi.rs`) builds local-prover's fixed six-account layout, signing `caller` via `caller_seeds`. Flash-Fulfiller uses its prover-scoped `prove_authority_pda`. Portal's `prove` assembles a variable account list and signs its prover-scoped `dispatcher` to a concrete prover. Aggregator validation is source-chain only; Portal’s `prove` dispatch still targets concrete provers.
- **Account creation** uses `eco_svm_std::account::create_account` (not Anchor's `init`) for griefing-resistant PDAs: it falls back to `transfer + allocate + assign` if the target was pre-funded.
- **The programs ship as one atomic release.** Portal, all provers and Flash-Fulfiller share the validation/closure ABI and PDA derivations. Build them from one tree. Releases derive each ID from the bytecode of the program and everything it compiles in, so a change to any of them moves every program bound to it, and a deploy covers exactly the programs whose addresses moved. `dispatcher_pda(prover)` and `prove_authority_pda(prover)` remain prover-scoped; `proof_closer_pda(intent_hash)` is intent-scoped. A mismatched tree can reject proof queries or cleanup authority. Provers must remain executable and implement the documented `Option<Proof>` interface; never turn a failed CPI into a `None` result.
- **Release program IDs are derived, not committed.** The committed `declare_id!`s are placeholders that never change. `scripts/program-keypairs.mjs` (zero-dependency Node 22; tests in `program-keypairs.test.mjs`, run by PR checks) derives each program's `Eco`-prefixed keypair from `PROGRAM_KEYPAIR_SECRET`, its lib name and a seed hashing its salt (`scripts/program-salts.json`, only ever raised), its placeholder builds (both clusters) and the seeds of the released programs whose IDs it compiles in — Cargo dependencies through shared crates, plus the aggregator's members. CI derives addresses only; keypair files exist only on the deployer's machine. Unchanged bytecode keeps its address; a change moves its dependents too. `release.yml` (manual; its `dry_run` input, on by default, builds and derives everything but publishes nothing) builds all released bytecode with `scripts/verifiable-build.sh` (`solana-verify build` in the digest-pinned `VERIFY_IMAGE`; never `anchor build`, whose output does not match deployed or verified bytecode), takes IDLs from `anchor idl build`, rewrites the `declare_id!`s before the real build, publishes `program-ids.json`, and pushes a `deploy/v<version>` tag (that rewrite committed on top of the release commit) for `solana-verify verify-from-repo`; it never reaches `main`, and its PDA goldens are stale by design. Never bump Cargo.toml versions before a release build (it changes the bytecode of `eco-svm-std`'s dependents), and never change the derivation `DOMAIN` in place — it moves every program.
- **Programs are redeployed, never upgraded in place.** A program's ID is derived from its bytecode, so any layout change moves it to a new ID, and every account here is a PDA of the program, so the new deployment starts on a disjoint namespace — no account written under an older layout is ever read back. An unchanged program keeps its address across releases. Account layouts (`FulfillMarker`, `WithdrawnMarker`, `Proof`, …) may therefore grow or be reordered freely, and **no layout migration or old-layout fallback should ever be written**. The flip side: under an in-place upgrade any of those changes would strand live intents (a grown `FulfillMarker` makes `prove`'s `try_deserialize` fail on pre-upgrade markers), so the redeploy assumption is load-bearing, not incidental.

### flash-fulfiller heap requirement

**Every transaction calling any flash-fulfiller instruction must prepend** `ComputeBudgetInstruction::request_heap_frame(256 * 1024)`. The crate installs a 256 KB `BumpAllocator` as `#[global_allocator]` (gated on the `custom-heap` feature, default-on) — Solana's stock allocator hardcodes 32 KB regardless of the heap-frame request. Without the request, the first heap allocation access-violates immediately. See `programs/flash-fulfiller/src/lib.rs` for the gory details and the `not(feature = "no-entrypoint")` gate that prevents the allocator from leaking into dependent programs that import flash-fulfiller for CPI types.

In `flash_fulfill`, `strip_call_accounts` truncates each call's Borsh tail in-place rather than deserialize/reserialize — the bump allocator never frees, so a round-trip retains ~3× the call size and pushes deep CPI chains into OOM.

## Integration tests (`integration-tests/`)

Use `litesvm` (not `solana-program-test`). `tests/common/mod.rs::Context` loads each program's compiled `.so` from `target/deploy/` via `include_bytes!`, so a build must precede a test run. The `Context` helpers (`rand_intent`, `set_mint_account`, `airdrop_token_ata`, `set_proof`, `set_token_account`, `set_withdrawn_marker`, `warp_to_timestamp`, etc.) are how all integration tests construct state. Add new shared helpers there rather than duplicating setup in test files.

Per-program contexts live next to `mod.rs`: `portal_context.rs`, `hyper_prover_context.rs`, `local_prover_context.rs`, `aggregator_prover_context.rs`, `flash_fulfiller_context.rs`, `hyperlane_context.rs`, `proof_helper_context.rs`, `polymer_prover_context.rs`, `layerzero_prover_context.rs`. They host the per-instruction builders that integration tests call.

Event assertions: `contains_event` (top-level `Program data:` log), `contains_cpi_event` (inner-instruction event_cpi), `contains_event_and_msg`. Error assertions: `is_error(SomeError::Variant)` matches `InstructionError::Custom`.

Aggregator tests check proof return data, subset queries and complete-membership absence, variable-sized account groups and child data, independent leaf cleanup and real Eco Hyperlane/Polymer delivery followed directly by settlement. Shared proof instruction discriminators and generated IDLs must agree.

**Closed accounts assert `get_account(&x).is_none()`, not a drained husk.** litesvm garbage-collects zero-lamport accounts, so a closed account is simply absent afterwards and its `owner`/`data` cannot be inspected. That matches real Solana, which also purges zero-lamport accounts at transaction end — the older `owner == system_program::ID` form was reading a simulator artifact, not a protocol guarantee, and cannot be restored. Anchor's `.close()` is what reassigns the owner; the property worth asserting here is that the account is gone and, where the rent recipient is a dedicated PDA rather than the fee payer (e.g. hyper-prover's `pda_payer`), that the rent came back.

## Goldie

Many tests use `goldie::assert_json!` / `assert_debug!` / `assert_yaml!`. Snapshots live in a `testdata/` directory next to the source file the test is declared in (e.g. a test in `programs/portal/src/state.rs` snapshots to `programs/portal/src/state/testdata/`) — goldie 0.7 nests per-module rather than sharing one flat `<crate>/src/testdata/`. Update with `GOLDIE_UPDATE=1 cargo test` and review the diff before committing.
